# M2.5 Concurrency proof and docs

**Goal:** the strongest engineering claim, no double booking under concurrent approvals, is visible in the app and verifiable in one command.
**Depends on:** M1 approve transaction. **Spec:** design.md "E2 Watch the race", "/autoplan #2" Phase 3 items 1-3 and Phase 3.5.

## Scope
- `approve(ctx, {afterRead?})` hook, no-op in production.
- `POST /api/demo/race`: hidden race person + two hidden projects per sandbox (`demoInternal`), per-session lock (`RACE_IN_PROGRESS`), barrier per run, first attempt only, 2s timeout (`RACE_TIMEOUT`), cleanup in `finally`, `DEMO_ROUTES_ENABLED` gate, `DEMO_ONLY` outside sandboxes.
- `/how-it-works` page: two swimlanes on a shared ms axis, barrier as a vertical rule, losing write in red with the real replay; states idle/running/result/rate-limited/waking.
- `pnpm demo:race`: runs against MongoMemoryReplSet and prints lanes, result and replay count.
- README: quantified headline decision first, "Hard problems" second (links test files and `demo:race`).
- `docs/architecture.md`: "Concurrency proof", "Scenario verdict", "Tenant isolation".
- ADR 0001: MongoDB + version bumps vs Postgres exclusion constraints.

## Tests
20-run exactly-one-winner; replay never waits at the barrier; timeout; lock; cleanup on throw; only the demo route passes `afterRead`; `demoInternal` excluded from candidates, stats, notifications, snapshots; e2e race page shows one success and one `CAPACITY_EXCEEDED`.

## Done when
`pnpm demo:race` prints the race in under 2 minutes from a fresh clone; the race page works on the deployed demo; README and architecture doc published.

## Implementation notes (eng review, 2026-11-03)
Checked against the merged M1-M3 code.

1. **A throwaway race org instead of hidden `demoInternal` fixtures.** Since M3 the sandbox is read by many more queries (projects, departments, members, approvals, the no-approver list, skills); each would need a `demoInternal` filter, and one missed filter leaks the fixtures. Each run instead creates its own tiny org (a manager, a person in their department, two projects, two 5 h proposals), runs the race through `orgRepo` for that org, and deletes every document with its `orgId` in `finally`, with `expiresAt` set as a backstop for the TTL indexes. Tenant isolation keeps it invisible by construction, and the "excluded from candidates, stats, notifications, snapshots" tests become one test: nothing of the race org remains, and the visitor's sandbox is untouched.
2. **The hook is in the real `approve()`.** `approve(ctx, id, version, { afterRead })` calls `afterRead` after the capacity read *and* check, right before the first write, on every attempt. Both lanes therefore pass the check against the same state; only the `capacityVersion` write conflict stops the second, which the driver replays, and the replay's re-check throws `CAPACITY_EXCEEDED`. Production passes nothing; a test asserts `afterRead` appears only in `assignments.ts` and the race service.
3. **The barrier.** Per run, two parties, first attempt only (a lane's later attempts pass straight through and are recorded as the replay), 2 s timeout (`RACE_TIMEOUT`, injectable for tests).
4. **Timeline.** Each lane records real offsets from the run start: `start`, `read` (hook, first attempt), `released` (barrier), `replay` (hook, later attempts), and the outcome (`committed`, or `refused` with the error code). Both lanes committing is logged at error and answered as `INVARIANT_BROKEN` (should never happen).
5. **Gates.** Demo sessions only (`DEMO_ONLY`), `DEMO_ROUTES_ENABLED` (default on), one run at a time per session (`RACE_IN_PROGRESS`), 5 runs per minute per session.
6. **Docs.** `docs/architecture.md` (concurrency proof, scenario verdict, tenant isolation) and `docs/adr/0001-mongodb-capacity.md` ship with this milestone, plus the README "Hard problems" section.
