## Problem Statement

Rebuild the ASSIST Tech Challenge 2024 "Team Finder" SRS as a portfolio project. The SRS describes a multi-tenant web app where organizations document employee skills, project managers find available people with matching skills, propose them onto projects, and department managers approve or reject. The goal is not to score the 500-point rubric; it is to produce a live app and repo that make a hiring manager or recruiter, skimming for ~2 minutes, conclude "this person ships clean full-stack + AI work."

Read straight off the spec, this is ~20 CRUD forms. The interesting part is one surface: staffing a project under real constraints (8h/day capacity, date ranges, skill levels 1-5, past-project similarity, approval by another role). Everything else in the SRS exists to feed that surface with data.

## What Makes This Cool

**A team-first canvas instead of a schedule-first grid.** Commercial resource tools (Runn, Kantata, Float, Planview) start from a people-by-weeks heatmap and treat skills as a filter. This app starts from the *shape of the team*:

- Role slots generated from the project's Team Roles (e.g. 2x Backend Dev, 1x QA).
- A ranked candidate sidebar; each card shows a score with a breakdown (skill fit, availability, past-project similarity) and why-chips ("frees up Apr 2 from Project Atlas", "Teaches React, 4-7 yrs").
- Drag a card into a slot: capacity bar updates (hours left of 8), required-skill coverage meter fills, overbooking turns the slot red before you commit.
- Ghost cards for people rolling off other projects within N weeks, shown with "available from <date>".
- Each drop creates a *proposal*; the slot shows "pending approval" until the department manager approves via the normal workflow.
- Stretch: a start-date scrubber. Slide the project start date and watch ghosts become available and gaps close ("Waiting until Nov 16 fills Backend without overbooking Alex").

## Constraints

- **Audience:** recruiters / hiring managers; ~2 minutes; many will only read the README.
- **Time:** 1-2 months of evenings. Full SRS (core + nice-to-haves) is the eventual target.
- **Stack (user choice):** React SPA + Node.js + NoSQL (MongoDB).
- **Deploy:** any cloud; Azure not required (SRS requirement waived for portfolio).
- **SRS fidelity:** keep the SRS rules (role stacking, 1 manager per department, skill ownership by creator, project deletion only if never In Progress/Closing/Closed, N between 2 and 6 weeks, hours 1..remaining) because they are what make the domain non-trivial.

## Premises (agreed)

1. **Plain screens, first-class invariants.** The canvas is the only hero-polished surface. All other SRS screens (departments, skills, roles, approvals, views) use clean consistent components with no hero treatment, BUT capacity, date-overlap, tenant isolation, and approval atomicity are treated as first-class engineering with tests and atomic writes. *(Revised after cross-model challenge.)*
2. **No signup wall on the demo.** The live URL opens into a seeded org with a role switcher (Project Manager / Dept Manager / Org Admin / Employee). Real auth (Auth-01..03, invite URL) exists and works behind it.
3. **Deterministic, explainable ranking first; LLM second.** The scoring engine is pure code with a visible breakdown. AI-01 (as revised at the /autoplan gate, see "AI-01") lets the LLM draft a team *only from the engine's top-ranked candidates*, seen pseudonymously; the engine validates every placement and nothing is proposed without the PM. The LLM never ranks, never sees names, and never commits anything.
4. **MongoDB with a separate `assignments` collection,** not embedded in users or projects. Availability is computed from it.
5. **MVP done (end of M1) =** live URL, README with a 30-second GIF at the top, CI running domain unit tests + one Playwright e2e of the canvas flow. The v1 target is the Success Criteria section below.

## Cross-Model Perspective (Codex, cold read)

- **Coolest unconsidered version:** compare two possible teams across time: "Start Monday" vs "Wait two weeks", with a scrubber that shows gaps closing. Gives the GIF a story: constraint, experiment, better decision. (Adopted as stretch milestone M6.)
- **What reveals the excitement:** "drag ranked candidates from a sidebar into slots": making a complex decision tangible with immediate consequences. Spend the best engineering hours on that feedback loop.
- **50% head start suggested:** Payload CMS (auth, access control, admin UI, Mongo, multi-tenant plugin). *Not adopted:* it is Next.js-based and conflicts with the React SPA choice and the learning goal; hand-rolled Fastify is easier to explain in interviews.
- **Weekend build:** one complete staffing decision end-to-end (8 employees, 1 project, 3 slots, one great-but-unavailable, one partial fit, one rolling off), deployed, with approval changing capacity and rejecting a conflicting allocation. (Adopted as M1.)
- **Challenged premise:** "rest of SRS is plumbing." Two managers can approve competing proposals against the same remaining hours. (Accepted; premise 1 revised.)

## Approaches Considered

### Approach A: Slice-first monolith
Express + Mongoose API and a Vite React app; ship the slice, then add features. Effort M, risk low. Ships fastest, but matching/capacity logic tends to leak into route handlers and the repo reads as tutorial-shaped.

### Approach B: Domain-core monorepo (CHOSEN)
pnpm workspace with a pure TypeScript `domain` package, a Fastify API, and a React web app sharing zod schemas. Effort L, risk medium. Detailed below.

### Approach C: Allocation ledger
Event-sourced assignments (proposed/approved/rejected/deallocated as append-only events, state as a projection). Time-scrubber and audit trail fall out of the model. Effort XL, high risk of overbuilding; the benefit is visible only to senior engineers.

## Recommended Approach: B — Domain-core monorepo

### Why the domain package is the center
- Ranking runs server-side only (`GET /projects/:id/candidates` returns ranked candidates with score breakdown, reasons, and a minimal per-candidate capacity timeline `[{from, to, hoursUsed, hoursPending}]`). The client re-runs `capacityOn()` from the same package only for the card being dragged, for instant feedback. Same code both sides, no drift, and the browser never receives org-wide assignments or skills.
- 100% unit-testable without Mongo. This is the code you walk an interviewer through.
- zod schemas are the single source of truth for API request/response types.

### Data model (MongoDB)
Every document carries `orgId`; every query is scoped by it (enforced in one repository layer, not per route).

- `orgs { _id, name, hqAddress, inviteToken }`
- `users { _id, orgId, name, email, passwordHash, accessRoles: ['employee'|'admin'|'deptManager'|'projectManager'], departmentId? }`
- `departments { _id, orgId, name, managerId? }` with a unique partial index on `managerId` (one department per manager).
- `teamRoles { _id, orgId, name }` (Role-02, informational only)
- `orgs` also carries `isDemo: bool`, `expiresAt?: Date` (demo sandboxes only).
- `users` also carries `capacityVersion: number` (see invariant 2).
- `skillUpgradeProposals { _id, orgId, userId, skillId, projectId, status: open|accepted|dismissed }` with a unique partial index on `(userId, skillId)` where `status = open` (Project-11).
- `skillCategories { _id, orgId, name }` (managed and reusable per Skill-01)
- `skills { _id, orgId, categoryId, name, description, authorId, departmentIds[] }`
- `userSkills { _id, orgId, userId, skillId, level 1-5, experience, validated: bool, endorsements[] }`
- `projects { _id, orgId, name, period: fixed|ongoing, startDate, deadline?, status, everActive: bool, description, techStack: skillId[], teamRoles: [{roleId, count}], skillRequirements: [{skillId, minLevel}], pmId, version }`
- `assignments { _id, orgId, userId, projectId, hoursPerDay 1-8, slotRoleId, roleIds[], status, from, to?, comments, deallocationReason?, approverId?, version }`. `slotRoleId` = the role slot this assignment fills (counted against `teamRoles[].count`); `roleIds[]` = all informational roles the person has on the team (SRS Project-03), always including `slotRoleId`. `approverId` = who actually decided (audit), not who is allowed to.
- `sessions { _id, orgId, userId, isDemo, expiresAt }` with a TTL index on `expiresAt` (server-side sessions, see Engineering decisions).
- `notifications { _id, orgId, userId, type, refId, readAt? }`

**Enums**
- Access roles: `employee | admin | deptManager | projectManager` (stackable).
- Skill level: `1 Learns | 2 Knows | 3 Does | 4 Helps | 5 Teaches`.
- Experience: `0-6m | 6-12m | 1-2y | 2-4y | 4-7y | 7y+`.
- Project period: `fixed | ongoing`; project status: `notStarted | starting | inProgress | closing | closed` (creation allows only the first two).
- Assignment status: `proposed | active | rejected | deallocationProposed | past`.
- Notification type: `assignmentProposed | deallocationProposed | proposalDecided | skillPendingValidation | skillUpgradeProposal | projectDeleted`.
- Dates: all assignment/project dates are UTC calendar days (`YYYY-MM-DD`); "today" is the UTC date on both client and server.

`techStack` references skills (not free text) so matching is exact. Project status changes go through one domain function `transitionProject(project, next)`, which is the only place that sets `everActive = true` (on entering inProgress/closing/closed); deletion requires `everActive === false` plus a confirm dialog. Transitioning to `closed` moves every started `active`/`deallocationProposed` assignment (`from <= closeDate`) to `past` with `to = closeDate`, rejects not-yet-started ones and open `proposed` ones (never producing `to < from`), and bumps `capacityVersion` for each affected user plus `projects.version`, all in one transaction.

**Project date edits clamp, never rewrite.** Assignment dates record actual participation; project dates are the schedule. On a start/deadline edit, for each non-past assignment: `from = max(assignment.from, newStart)`; `to` moves to the new deadline only if it equaled the old deadline (a deliberately shorter allocation keeps its `to`). The edit runs in one transaction that re-checks invariant 1 for each affected user, bumps their `capacityVersion` and `projects.version`; if any user would be overbooked, it fails with a 409 listing them. Upgrade-proposal clocks (Project-11) use the assignment's `from`, so they move only when a clamp moves it.

**Assignment dates.** A proposal carries its own `from` (default = start of the evaluation window; for a rolling-off "ghost" candidate = their `availableFrom`; editable in the drop popover, must be inside the project window). Approval keeps that `from` (bumped to today if it is already past). `to` = project.deadline for fixed projects, `null` (open-ended) for ongoing projects, and set to the approval date when a deallocation is approved.

**Project conflict boundary.** Every transaction that creates or changes assignments of a project (propose, approve, reject, deallocate, project delete, close, date edit) calls one helper `touchProject(session, projectId)` that increments `projects.version`. Combined with the per-user `capacityVersion` bump, any two such operations on the same project or the same person write a common document and conflict, so the driver replays one of them against fresh state.

**Slot limits.** Propose checks, inside the transaction, that count of `proposed|active|deallocationProposed` assignments with this `slotRoleId` < the role's `count`, else `SLOT_FULL`. A person holds at most one non-terminal assignment per project.

**Skill validation (Skill-04).** Before M4, all userSkills are created `validated: true`. Once Skill-04 ships, self-assigned skills are created `validated: false`, are visible only to the owner (marked "pending") and their department manager, and are ignored by the matching engine and stats until validated.

### Assignment state machine
| From | To | Triggered by | Side effects |
|---|---|---|---|
| (none) | proposed | PM of project | Notify employee's dept manager. Rejected if the user already has a non-terminal assignment on this project, if the slot is full (`SLOT_FULL`), or if the employee has no approver (`NO_APPROVER`). Re-proposal after `rejected` or `past` is allowed (new document). |
| proposed | active | Employee's dept manager | Atomic capacity check (invariant 2) from the proposal's `from`; set `to`; notify PM. |
| proposed | rejected | Employee's dept manager | Notify PM. |
| active | deallocationProposed | PM of project | Requires reason; notify dept manager. |
| deallocationProposed | past | Dept manager | `to = now`; notify PM; frees capacity. |
| deallocationProposed | active | Dept manager (reject) | Notify PM. |

- **Who approves:** resolved at decision time, never stored: the manager of the employee's *current* department. The approvals inbox query joins pending items on the employee's current department, so moving an employee re-routes their pending items automatically; the old manager loses access.
- **Employee with no department, or department with no manager:** the user cannot be proposed (the candidate card shows "no approver: assign to a department first"). Items already pending for such a user appear in the org admin's "no approver" list. No admin fallback, to keep one approval path.
- **Project deletion:** only possible when `everActive === false`. Deletes all of the project's assignments (any status) in the same transaction, which frees any capacity held by `active` ones, and sends a `projectDeleted` notification to each affected dept manager.
- **Capacity states:** `active` AND `deallocationProposed` consume capacity (the person still works there until the manager agrees). `proposed` does not consume capacity but is shown as pending: the CapacityTimeline carries `{used, pending}` per segment and the canvas draws pending as a striped segment with a warning when `used + pending > 8`.

### Matching engine (domain)
Inputs: project, options `{includePartial, includeRollingOffWithinWeeks: 2..6 | null, includeUnavailable, includeNearMisses}`, candidates with skills, assignments, and past projects.

- **Evaluation window:** everything is evaluated over the project window `W = [max(today, project.startDate), project.deadline)`, open-ended (`[start, ∞)`) for ongoing projects. The same window definition is used by ranking, the canvas preview and approval. Because a CapacityTimeline has finitely many breakpoints, the minimum over an open-ended window is exact.
- **Availability:** `hoursLeft(user, date) = 8 - used(date)` where `used` sums `active` and `deallocationProposed` assignments overlapping the date. Fully available = `hoursLeft = 8` on every day of W. Partially available = `0 < min hoursLeft over W < 8`. Rolling-off (SRS: "projects close to finish") = the user is unavailable at the start of W, but every blocking assignment is on a fixed project whose `deadline` falls within N weeks of W's start; `availableFrom` = latest such deadline. Assignments on ongoing projects never count as rolling off.
- **Filter:** per SRS options; default = fully available only. Candidates must also match at least one tech/requirement skill OR have a past project sharing tech and roles (SRS "AND/OR").
- **Score (0-100), each term returned separately for the UI:** `score = 60*skillFit + 25*history + 15*availability`
  - `skillFit` (0..1): mean over the project's targets = the deduplicated union of techStack skills and skillRequirements skills (a skill in both counts once, with its minLevel). Per target: `0` if the user lacks it; else `(level/5)*0.8 + expIndex/5*0.2` where expIndex is the experience enum position 0..5. If a requirement has `minLevel` and the user is below it, the candidate is excluded (gate), with reason `belowMinLevel` shown when "include near-misses" is toggled.
  - `history` (0..1): max Jaccard similarity of (techStack ∪ roleIds) between this project and each of the user's past projects (the user's assignments with status `past`).
  - `availability` (0..1): `hoursLeft / 8` if available now; `max(0, 1 - weeksUntilAvailable / 6)` for rolling-off candidates; `0` for unavailable.
  - Ties broken by name for determinism.
  - Weights live in one exported constant so they can be tuned and tested.
- **Explanations:** engine emits structured reasons (`{kind: 'rollsOff', project, date}`), and the UI renders them as chips. No string building in the engine.

### Invariants (tested, enforced server-side)
1. **No overbooking:** sum of hoursPerDay of `active` + `deallocationProposed` assignments for a user on any date <= 8.
2. **Atomic approval:** approve runs inside `session.withTransaction(cb)`. The callback (a) reads the user's overlapping capacity-consuming assignments with the session, (b) rechecks invariant 1 via `withProposal(buildTimeline(...))`, (c) updates the assignment with an optimistic `version` check, (d) increments `users.capacityVersion`, and (e) calls `touchProject()`. Step (d) prevents write skew: two approvals of *different* proposals for the same user both write the same user document, so one hits a write conflict (`TransientTransactionError`). The driver replays that callback automatically; on replay it sees the other approval, the recheck fails, and the callback throws a non-transient `CapacityError`, which maps to 409 `CAPACITY_EXCEEDED`. No hand-written retry loop (the driver also handles `UnknownTransactionCommitResult`; its retry window is 120s). Tested with two *different* proposals approved concurrently: exactly one succeeds. (Requires Atlas or a replica set; a standalone mongod has no transactions.)
3. **Tenant isolation:** no API route returns or mutates a document with a different `orgId` than the caller's. Enforced structurally: routes never get the raw `Db`; they get `orgRepo(request.actor)`, which wraps each collection and injects `orgId` into every filter, insert, update and the first `$match` of every aggregation. An ESLint `no-restricted-imports` rule forbids importing the Mongo client outside `apps/api/src/db/`. Every index leads with `orgId`. Covered by an API test that creates two orgs and attempts cross-org reads/writes on every resource type.
4. **Role rules:** SRS permission matrix as a pure `can(user, action, resource)` function in `domain`, unit-tested as a table.
5. **Date semantics:** intervals are half-open `[from, to)`; ongoing projects have `to = null` (open-ended). One shared `overlaps()` helper.

### Engineering decisions (from /plan-eng-review)
```
 Browser (React SPA)                 same origin: /api/* proxied        Fastify API                          MongoDB Atlas (replica set)
 ┌──────────────────────────┐  ───────────────────────────────────▶  ┌──────────────────────────────────┐  ┌──────────────────────┐
 │ Canvas (dnd-kit)         │   first-party SameSite=Lax cookie       │ preHandler resolveActor()        │  │ sessions             │
 │  withProposal(timeline)  │                                         │  -> request.actor{userId,orgId,  │  │ orgs users ...       │
 │  (packages/domain)       │  ◀── ranked candidates + timelines ──── │      roles,isDemo}               │──│ assignments          │
 │ TanStack Query           │  ◀── DomainError JSON on 4xx ────────── │ routes -> services -> orgRepo()  │  │ projects (version)   │
 └──────────────────────────┘                                         │ approve(): withTransaction       │  └──────────────────────┘
                                                                      └──────────────────────────────────┘
```
- **Same-origin API.** The SPA host rewrites `/api/*` to the API service, so the browser sees one origin and the session cookie is first-party (`HttpOnly; Secure; SameSite=Lax`). Avoids Safari/Chrome third-party cookie blocking killing the demo.
- **Auth seam from M1.** Sessions live server-side (`sessions { _id, orgId, userId, isDemo, expiresAt }`, TTL index). One Fastify `preHandler` resolves `request.actor = {userId, orgId, roles, isDemo}`. "Try the demo" and the role switcher create/replace a session; M2 password login creates the same session type. Routes and `can()` only ever see `actor`.
- **One capacity representation.** `packages/domain` exports `buildTimeline(assignments) -> CapacityTimeline` (sorted, merged segments of `{from, to, used, pending}`) and `withProposal(timeline, hours, from, window) -> {fits, worst: {date, used}}`. Ranking, the approve invariant and the canvas all consume a CapacityTimeline; the server sends timelines, never raw assignments. Property-tested with fast-check.
- **Typed errors.** `packages/domain` exports a zod discriminated union `DomainError`: `CAPACITY_EXCEEDED{userId,date,used,requested}`, `SLOT_FULL{roleId}`, `NO_APPROVER{userId}`, `FORBIDDEN`, `CONFLICT_STALE`, `NOT_FOUND`, `VALIDATION{issues}`. One Fastify error handler maps them to HTTP status; the web app has one `toErrorMessage()`.
- **Batched ranking inputs.** `GET /api/projects/:id/candidates` loads inputs in 4 queries (users, userSkills, capacity-relevant assignments overlapping W, past assignments + their projects via `$in`), then calls pure `rankCandidates(inputs)`. Indexes: `assignments {orgId, userId, status, from}`, `assignments {orgId, projectId, status}`, `userSkills {orgId, userId}`. A test asserts the query count stays at 4.

### Canvas UX notes
- Optimistic UI on drop (domain computes the new capacity locally), confirmed by the API; on 409, snap back with the reason shown.
- Drop opens a small popover: hours/day (1..hoursLeft), start date (prefilled; `availableFrom` for ghosts), extra roles, comment.
- After a role switch, invalidate all TanStack Query caches so the PM sees approvals immediately.
- Slot states: empty, pending proposal, active, conflict (red).
- Keyboard-accessible alternative to drag ("Add to slot" menu) for a11y and for the Playwright test.
- Empty state: if no candidates match, show which filter excluded the most people ("12 people excluded by full-availability filter: include partially available?").

### Public demo mode
No shared demo org and no unauthenticated role switcher on real data. "Try the demo" creates a disposable sandbox org per visitor (cloned from a seed template via a script that inserts ~60 users / 12 projects with fresh ids), issues a signed httpOnly demo cookie bound to that `orgId`, and enables the role switcher only for orgs flagged `isDemo`. The switcher impersonates seeded users within that org only. Sandboxes expire after 24h (TTL index on `orgs.expiresAt` plus a cleanup job for child collections). Rate-limit sandbox creation per IP.

| Type | Recipient | Trigger |
|---|---|---|
| assignmentProposed | employee's dept manager | proposal created |
| deallocationProposed | employee's dept manager | deallocation proposed |
| proposalDecided | PM of project | dept manager approves/rejects either kind |

### Project-11 (skill upgrade proposals)
A daily job finds active assignments that crossed a 3-month multiple since `from`. For each project skill requirement / tech skill the user lacks or holds below the requirement's `minLevel`, it inserts a `skillUpgradeProposals` doc (the unique index dedupes open proposals per user+skill) and a notification. The employee can accept it by picking level and experience (same form as Skill-02).

### AI-01 (LLM drafts a team, engine validates) — chosen at the /autoplan gate
The PM describes the need in plain language. The backend sends the text, the org's skill/role vocabulary, and the top-ranked candidates' **pseudonymous** summaries (`c1..cN` with skills, levels, availability windows; no names or emails) to the LLM with a JSON schema for `{ assignments: [{candidateRef, slotRoleId, hoursPerDay, from}], rationale: string[] }`. The server maps refs back to users, then runs every draft assignment through the same domain checks as a manual drop (`withProposal`, slot limits, approver exists). The canvas shows the draft as ghost placements with a per-slot verdict (fits / conflict with reason) and the rationale; the PM accepts slots individually, which creates normal proposals. The LLM never commits anything and never sees PII. Raw JSON is logged to the browser console per SRS. If `LLM_API_KEY` is unset or the call fails (`AI_UNAVAILABLE`), the panel says so and manual staffing is unaffected.
